# Native `st` help audit (agent use)

Scope: SummitFlow-owned routes registered from `backend/cli/main.py` and `backend/cli/commands`. The adjacent `native-audit.json` retains 243 native Click routes (212 commands, 31 groups, including root/task aliases), each captured summary, visible and hidden options, defaults, and callback source location. It also lists 46 manually dispatched `st db` and `st check` paths, for 289 documented native paths total. Generated extension namespace handlers are excluded. I built the graph with `typer.main.get_command` and `inspect.unwrap`, then inspected help output and implementation source; I did not invoke mutating callbacks. Source checks focused on claims that affect an agent's choice or next action. This is not an execution proof for every remote backend response. The retained inventory records the audited source; no native Click command has a blank summary in that snapshot.

## Findings

1. **High — `st autocode --at` reports a schedule but dispatches immediately.** `tasks.py:327-336` exposes `--at`; `tasks_autocode.py:29-36` parses it but calls `_queue_task_for_execution` without passing the schedule. That function calls `client.execute_task(task_id)` (`tasks_autocode.py:167-173`), whose API immediately calls `dispatch_task(..., manual_dispatch=True)` (`app/api/tasks/update_endpoints.py:261`). The CLI then emits `status=scheduled` and `scheduled_for` (`tasks_autocode.py:176-189`). An agent trusting the result may start work before its requested time. Reject `--at` with an explicit unsupported message until it is backed by a real schedule, or implement and verify scheduling before advertising it. This is a functional defect surfaced by the help audit, not a wording-only fix.

2. **High — `st backup status [TASK_ID]` advertises an unsupported lookup.** The optional argument is labeled `Job ID` (`backup.py:400-403`), but any supplied value exits 1 with “Task status lookup not yet implemented” (`backup.py:409-414`). The no-argument path shows the latest backup. Remove/hide the argument from agent help and point task-specific lookups to a working route, or implement lookup; avoid a documented dead end.

3. **Medium — `st backup create --dry-run --source X` is not a preview.** The command help says dry-run scans the local project tree and reports included/excluded counts and size (`backup.py:96-109`). For a source ID, `_create_backup_dry_run` only prints a note and returns, with no scan (`backup.py:138-163`). Qualify the help: the detailed scan applies to project backups; a source dry-run cannot preview the server archive. The `--dry-run` option summary should make this distinction before an agent relies on it.

4. **Medium — `st pulse --project` describes the default backward.** The option says it selects one project “instead of the global overview” (`pulse.py:151-157`), but `_resolve_project_ids` first uses the current detected project when `--all` is absent (`pulse.py:26-46`). The global overview occurs without a project only when none is detected, or with `--all`. Say “Select one project; defaults to the detected project. Use `--all` for every project.”

5. **Medium — `st service rebuild` misdirects scope and one usage example.** The `--scope` option says “Explicit isolated component” (`service.py:180-185`), while the implementation states that stable releases build the full accepted source and only restart scope remains selected (`service.py:226-232`; build steps at `service.py:257-262`). State that scope selects restart/migration targets, while release construction remains full-source. The `@usage` example `st -P agent-hub service rebuild` (`service.py:164-170`) omits the required `project` argument (`service.py:174-176`); replace it with `st service rebuild agent-hub` or include the positional even with global `-P`.

6. **Medium — dependency-review route omits its required continuation contract.** `st tools dependencies list`, `review`, and `record` have blank command summaries in live help (`tools_dependencies.py:25-90`). `record --revision` and `--reason` are required but have no help; `record_decision` expects the current evidence revision and rejects stale revisions (`app/services/dependency_management.py:251-269`). Add concise list → review → record descriptions, show where `revision` comes from, explain `--queue`, and describe filters such as `--status` before use. This is the most important missing native command-level guidance outside root aliases.

7. **Medium — `st create --dry-run` appears universal but fails for a bare title.** `tasks.py:36-65` exposes `--dry-run` without help; `tasks_create.py:111-114` rejects it unless `--plan` or `--from-file` is provided. Give the flag a description that identifies those two modes, including the failure condition.

8. **Low — `st sessions monitor --limit` changes units by mode.** Shared option help says “Maximum events to show” (`sessions_options.py:43-47`). Targeted session mode uses event count (`sessions.py:232-241`), while overview passes it as a session limit (`sessions.py:277-297`). State “Max sessions in overview; max events for a session target” so an agent can bound output correctly.

9. **Low — `st check --acceptance` help omits accepted control flags.** The general `st check --help` text lists `--sha`, `--task`, and `--scope` (`check_dispatch.py:269-286`), while its dedicated parser accepts `--no-reuse` and `--json`, and the nested `--acceptance --help` mentions both (`check.py:344-367`). Keep the two help paths consistent and briefly define whether reuse is the default. The existing named-tool list and `--quick`/`--changed-only` routes match dispatch at this level.

10. **Low — `st ready-all` priority description is imprecise.** Help says top tasks are prioritized “blocked first, then bugs, then by priority level” (`tasks.py:126-138`). Rendering presents active, stale, blocked, then ready sections; projects sort by blocked count, stale count, active count, ready count (`tasks_ready_all.py:203-253`). Describe the actual section order and per-project limit instead of implying one global task ranking.

11. **Low — `st create` usage metadata points to a Markdown plan.** Its `@usage` precaution said `--plan plan.md`, while the CLI help and importer require a JSON plan (`tasks.py:30-45`, `tasks_import.py:127-132`). The usage text now says `plan.json`.

12. **Medium — manually dispatched `st db` help was identical for every subcommand.** `st db query --help`, `st db schema --help`, and `st db migrate create --help` all printed the root summary because `db.py:423` intercepted any `--help` before dispatch. The summary omitted `query --plain`, `migrate` argument/default contracts, and described `schema` as showing keys/constraints it does not query (`db.py:367-384`, `db.py:448-528`). Help now selects concise per-command syntax before project/database resolution, including the migration variants, and the root summary matches implemented introspection fields. A focused test asserts no database or migration callback runs for targeted help.

All twelve findings above have command-module fixes in the current working tree: `--at` now fails before any client method call, and the remaining fixes adjust help, usage metadata, or the source dry-run explanation without changing other flags/defaults. The parent owns `main.py` root registration/help and global output precedence; its concurrent root fix restored the `st create` and `st verify` summaries in the current route inventory. The optional legacy job-ID argument to `st backup status` remains accepted but is explicitly labeled unavailable, because its lookup is unimplemented.

Scoped `st check ruff -- ...`, `st check types -- ...`, and `git diff --check` passed. Rendered `st autocode --help`, `st backup create --help`, `st tools dependencies record --help`, `st service rebuild --help`, `st check --help`, and targeted `st db ... --help` showed the intended wording. No live database, backup, dispatch, or deployment was invoked.
