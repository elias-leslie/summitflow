## Existing SummitFlow surface before this implementation (inspected)

- `backend/app/services/resource_monitor.py` collects psutil host CPU, memory, disk and NVIDIA data. `backend/app/api/system.py` exposes current system stats. The reported response timestamp is not a source measurement timestamp; `get_cpu_usage` has a blocking one-second psutil call.
- `backend/app/services/runtime_metrics_sampler.py` samples managed service CPU/memory every 300 seconds by default and retains 14 days in PostgreSQL. FastAPI lifespan owns this sampler. `GET /api/docker/metrics` also writes a sample while serving live metrics. The systemd provider in `backend/app/api/docker/_metrics_collection.py` measures the main PID rather than a cgroup total.
- `backend/cli/commands/runtime.py` exposed `st runtime metrics` from the PostgreSQL store. `st logs` offered bounded service aliases but did not provide journal cursor/provenance or explicit source failures. Neither was an independent outage history path. The new standalone `st monitor` fills that gap.
- `frontend/app/(app)/runtime/page.tsx`, `ServiceGrid`, and `ServiceMetricTimeline` already offer health cards and service CPU/memory history. `backend/app/access_control.py` restricts general APIs to the owner, but sensitive monitor endpoints should also declare `require_owner` themselves.
- The backend and frontend run as managed user services; the owner user manager has lingering enabled. The current account belongs to `adm` and `docker`, so its successful reads do not establish ordinary-account coverage. Before the implementation, the `st` command resolved through the backend virtualenv. The installed launcher now dispatches `st monitor` through the accepted standalone reader.

## Build-versus-adopt decision

Build a small, local SummitFlow-owned collector/store/query model. It directly fits owner-only `st` access, backend-independent committed history, managed-service identity, and Runtime UI reuse. Profile adopt candidates where isolated execution is practical; do not claim measured comparative overhead for those not run. [Glances](https://github.com/nicolargo/glances/blob/b3f1cf008e9ad28eb02e1bb63d74f980683fedf6/pyproject.toml) (LGPL-3.0-only) is the strongest ready-made alternative: it already documents a [REST history API and Basic/JWT authentication](https://glances.readthedocs.io/en/latest/api/restful.html), plus an optional [MCP interface with per-plugin history resources](https://glances.readthedocs.io/en/latest/api/mcp.html). Adopting it would still require a demonstrated bounded, durable outage-history path and SummitFlow-specific owner principal, service identity, redaction, and process/event correlation; those are integration gaps, not missing general Glances capabilities. Its default web-server exposure needs explicit bind/auth configuration, per its own security documentation. [node_exporter](https://github.com/prometheus/node_exporter/tree/60ce437b9c737c3b9a9619df457ae68a067d3cfc) (Apache-2.0) supplies host counters but not process/log investigation or history by itself. [Netdata Agent](https://github.com/netdata/netdata/blob/d587983ee11c8994bad39682dcf28631c3000a69/REDISTRIBUTED.md) (GPL-3-or-later) and its [separately licensed UI](https://app.netdata.cloud/LICENSE.txt) add an independent stack. [btop](https://github.com/aristocratos/btop/tree/7b1f128e511ff5901dfba44dcd5f37236e7cb403) (Apache-2.0) is a UI reference, not the shared query system.

### Storage lessons from other monitors

[Netdata DBENGINE's published design](https://github.com/netdata/netdata/blob/master/src/database/engine/README.md) keeps metric pages in memory, compresses groups of up to 64 pages into append-only extents, and rotates whole datafiles. Its [retention documentation](https://learn.netdata.cloud/docs/netdata-agent/database) calls size limits soft targets, and its [database-engine documentation](https://learn.netdata.cloud/docs/developer-and-contributor-corner/database-engine) says unflushed hot and dirty pages can be lost in a crash. [Prometheus storage documentation](https://prometheus.io/docs/prometheus/latest/storage/) describes an in-memory head protected by a compressed WAL, then block compaction; its WAL keeps at least three 128 MB files, and size retention can temporarily exceed its target during compaction. A two-hour block is not a two-hour durability interval. [RRDtool](https://oss.oetiker.ch/rrdtool/doc/rrdtool.en.html) uses fixed-size round-robin archives and resolution consolidation; [rrdcached](https://oss.oetiker.ch/rrdtool/doc/rrdcached.en.html) reduces writes by holding updates in memory (300-second default write interval) and offers a recovery journal. These systems separate sampling resolution, durable commit cadence and retention, with different recovery and quota contracts. The Netdata code and UI are not being copied. No external system's published disk-per-sample figures predict physical writes on this Btrfs host.

The local metadata-compression replay reduced serialized bytes by 39.8% but physical writes by only 7.7%; that is insufficient to close the installed `FULL` write gap. The recommendation is to retain SQLite/WAL and five-second `FULL` commits while measuring the host's actual endurance and workload. An isolated append-only, five-second-`fdatasync` replay is the next experiment if the 1 GiB/day write target remains strict; it must include indexes, rotation, recovery and retention before justifying a production rewrite. [SQLite documents](https://www.sqlite.org/whentouse.html) the embedded application-store fit. [LMDB's published design](https://github.com/openldap/openldap/blob/master/libraries/liblmdb/lmdb.h) uses copy-on-write B-tree pages and serialized writes; its [OpenLDAP Public License](https://git.openldap.org/openldap/openldap/-/blob/LMDB_0.9.29/libraries/liblmdb/LICENSE) permits evaluation, but lower writes cannot be assumed. An additional engine is not justified by the current evidence.

TMOG's [official RTM page](https://www.tmog.org/rtm/) and [release notes](https://tmog.org/release-notes.html) describe the product; the installed Free views were observed, while Pro was available only as previews. The [feedback repository](https://github.com/PlummersSoftwareLLC/tmog-feedback/blob/72c6607244287ba77e147a180a28e2a5c6ffeec3/README.md) explicitly says product source is private. Its creator's separate [Windows console `tm`](https://github.com/PlummersSoftwareLLC/tm/tree/5fd5552c2c80bd4e08a862a4ccea9592abd928f8) has no license; do not reuse its code. The unaffiliated [evildojo-tmog](https://github.com/mikedesu/evildojo-tmog/tree/d63110ae031c1c220682e947215b12f7cab7c845) is MIT licensed and may inform ideas or fixture design with attribution. No TMOG proprietary implementation was inspected or copied.

## Collector comparison (measured prototypes)

The common contract is in `prototype-contract.md`; three local prototypes use psutil 7.2.2, gopsutil v3.24.5, and sysinfo 0.39.6 plus Linux proc/sys sources. Three balanced sequential rounds sampled a known SummitFlow service cgroup and about 695–712 visible processes in the corrected run. Values are median of runs, from `/tmp/sf-monitor-comparison-20260926-2/comparison.json` and protected retained evidence. Warm CPU uses cumulative process CPU changes between emitted samples, excluding startup.

| Mode | Python CPU / RSS | Go CPU / RSS | Rust CPU / RSS |
| --- | --- | --- | --- |
| Baseline, 5-second cadence | 1.00% of one core / 19.1 MiB | 0.36% / 9.6 MiB | **0.24% / 3.0 MiB** |
| Detail, 1-second cadence | 5.00% / 20.1 MiB | 1.67% / 9.7 MiB | **1.33% / 4.3 MiB** |

Sample-plus-common-SQLite-commit p95 was about 53/18/15 ms baseline and 53/18/15 ms detail for Python/Go/Rust. All three exposed the same ~38% per-process I/O coverage in detail because this host denies many `/proc/<pid>/io` reads; all retain those processes with null I/O. A semantic check fixed an early Python omission of denied rows and Rust loop-device double counting **before** the corrected comparison. Rust's cgroup units/keys were fixed and validated on the known service path. The common writer produced about 123 KiB of JSON per detailed sample and roughly 3.9 MiB of physical writes for ten detailed samples, including the raw NDJSON evidence file. This does not predict production write volume; continuous raw 1 Hz detail is incompatible with a small bounded store.

**Decision:** Rust was selected because it preserved tested field coverage and won CPU, RSS, and sample latency against Go in the corrected runs. The production service is now installed; [verification.md](verification.md) reports its separate managed profile and recovery checks. [sysinfo](https://github.com/GuillaumeGomez/sysinfo/blob/5bb745b85474c58a2435621b13ddbd491d63d58d/Cargo.toml) is MIT; [rusqlite](https://github.com/rusqlite/rusqlite/blob/91f876c80114122670f455190d03c81d1f78b0af/Cargo.toml) is MIT and [flate2](https://github.com/rust-lang/flate2-rs/blob/fcc804306677bf8cfde2250bf0472d61b75d1c45/Cargo.toml) is MIT OR Apache-2.0. The exact locked production graph resolved 87 crates offline with no missing license declarations and no nonpermissive license requirement; its own crate is Apache-2.0. This metadata check is not a legal opinion.

## Security and platform boundary

The installed non-root user service uses owner-only state/socket access and no collector network listener. That identity still has consequential group privileges; no arbitrary SQL, shell commands, journal arguments, or routine argv/environment/raw logs are exposed. Potentially destructive controls remain in existing `st` workflows. HTTP authorization still inherits SummitFlow's local-development owner bypass; the installed origin-LAN guard and remaining local multiuser limitation are described in [verification.md](verification.md).

Linux [proc visibility](https://www.kernel.org/doc/html/latest/filesystems/proc.html) and per-file permission checks limit other-user detail; [PSI](https://www.kernel.org/doc/html/latest/accounting/psi.html) and [cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html) expose useful pressure and service counters when configured; journal access is separately gated by [journal file permissions](https://www.freedesktop.org/software/systemd/man/latest/systemd-journald.service.html). [SQLite WAL](https://www.sqlite.org/wal.html) permits one writer and concurrent readers but needs short read transactions and explicit checkpoint/failure handling. Feature-detect all optional providers.

Basic cross-platform counters may reuse library abstractions. macOS and Windows require separate service managers, logging, process identity, sensor/power, startup, socket-ownership, packaging and permission providers. Keep Ubuntu as the verified first platform; estimate further platform work from provider spikes and actual Ubuntu implementation effort, not a calendar guess.
