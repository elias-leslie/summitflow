## Installed architecture

```text
/proc + /sys + cgroup v2 + systemd user units
                  │
        Rust host-monitor (user service)
        5 s baseline; bounded detail lease
                  │
       0700 state / SQLite WAL / 0600 socket
                  │
      monitor_reader schema v1 + on-demand providers
          ┌───────┴────────┐
    standalone st       owner Runtime API → Monitor UI
```

The collector is the sole writer. It persists source timestamps, gaps, error codes, service state, process identity `(boot_id,pid,start_ticks)`, baseline leaders and leased process detail. It stores neither argv/environment nor raw logs. On-demand journal, sensors, inventory, connections, scoped disk attribution and bounded probes do not become routine history. The standalone `st` launcher selects the accepted monitor release and still reads committed SQLite when the FastAPI/PostgreSQL import graph is unavailable. The managed unit uses systemd sandbox settings and has no network listener.

The corrected prior run extrapolated 0.907 GB/day baseline and 2.158 GB/day detail, showing short-run variance. A further live process-lifetime sample (`managed-mixed-so-far.json`) after 1,078 seconds and 12 detail rows among 216 baseline rows extrapolated **1.117 GiB/day**, above the original ≤1 GiB/day representative-mix write gate. A later read at 2,246 seconds and 12 detail rows among 450 baseline rows still projected **1.092 GiB/day**. These are developing-system windows, but they are measured failures, not passing acceptance. Leases expire, but repeated leases and sustained triggers can keep detail active. `sqlite-sync-replay.json` showed substantially fewer btrfs writes with WAL `NORMAL`, but [SQLite documents](https://www.sqlite.org/pragma.html#pragma_synchronous) possible loss of committed transactions after OS crash or power failure; the owner chose to keep `FULL` durability. `sqlite-checkpoint-replay.json` found no repeatable physical-write reduction from higher or manual checkpoint thresholds while retaining `FULL`; [PASSIVE checkpoints](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint) may stop short behind an active reader.

The current migrated **512-byte-page, FULL-durable, checksummed Btrfs** release was profiled for 600.032 seconds of baseline plus 35.04 seconds of leased detail; raw evidence is `managed-profile-512-full.json`. Baseline used 0.38% of one CPU core, 5.000 MiB median / 5.602 MiB peak cgroup memory, 7,651,328 PID write bytes over 121 commits, and 39.052 ms sample-plus-commit p95. Detail used 2.489% of one core, 6.715 / 7.172 MiB memory, 888,832 write bytes over seven commits, and 73.13 ms p95. The observed mix, 35.04 / 635.072 seconds of detail duty, extrapolates **1,161,867,983 bytes/day = 1.082 GiB/day**, still **above** the ≤1 GiB/day target by about 7.6%. Status/process/series CLI p95 were 102.942 / 41.203 / 42.401 ms. `managed-512-io-trace.json` independently sampled PID I/O each second for 120 seconds: 24 nonzero five-second intervals and one larger checkpoint burst. These are `/proc/<pid>/io` write bytes, not per-device wear accounting. A longer stated mixed-load/churn profile and a repeatable FULL-durable reduction are needed to close the write gate.

The next installed profile (`managed-profile-gzip6.json`) used 600.100 seconds of baseline plus 35.023 seconds of detail, a matching 5.514% duty cycle. Baseline consumed 0.442% of one CPU core, 5.117 MiB median / 6.539 MiB peak cgroup memory and 8,187,904 PID write bytes over 120 commits; detail used 2.804% of one core, 8.221 / 8.473 MiB memory and 1,486,848 write bytes over seven commits. Sample-plus-commit p95 was 70.0 / 72.437 ms; status/process/series CLI p95 was 105.801 / 47.172 / 47.951 ms. Combined writes extrapolate **1,316,120,772 bytes/day = 1.226 GiB/day**, a measured failure of the write gate. Recent baseline process blobs became smaller (median 1,199 to 930 bytes), and detail blobs fell from about 20,879 to 13,963 bytes, but this short live window wrote more physical bytes than the prior one. Different process counts, checkpoint phases and a brief concurrent isolated Rust build limit causal attribution; the gzip replay percentage must not be projected onto the live host. A longer baseline follow-up and metadata-compression replay are below.

The subsequent baseline-only follow-up (`gzip6-baseline-followup-15m.json`) observed 196 baseline commits and zero detail rows over 978.9 seconds with the same collector PID. Its 13,733,888 PID write bytes extrapolate **1.129 GiB/day**. This longer interval still exceeds the combined-use goal before detail is added; the ordinary baseline write path needs improvement. The follow-up overlapped isolated GPU build/profile work elsewhere on the Btrfs host, but its I/O counter is for the collector PID.

`metadata-paced-ab.json` compared TEXT host/service/error columns with a temporary gzip-6 BLOB codec under the actual Rust Store's 512-byte-page, `FULL`/COW and five-second cadence. Over 120 baseline and seven paired detail writes per arm (595 seconds), serialized payload fell 596,817 → 359,538 bytes (39.76%), but physical writes fell only 8,888,320 → 8,204,288 bytes (7.70%). Store CPU rose 346.0 → 358.6 ms and all-commit p95 changed 26.49 → 27.27 ms. Both stores passed integrity checks and all 180 rows decoded exactly. Reaching 1 GiB/day from the installed 1.226 GiB/day needs about 18.4% reduction; this isolated saving is too small, and changing the TEXT columns would require a coordinated reader migration. No production codec or service changed. The working hypothesis is transaction/checkpoint write amplification rather than metadata size alone. Astra independently recommended retaining SQLite pending a complete paced append-only/recovery comparison.

The owner challenged the practical value of optimizing a 0.226 GiB/day miss against a 1 GiB/day investigative write target on a host that rarely crashes. That difference is cumulative write activity (about 82 GiB/year if sustained), **not retained disk growth**; raw samples expire after 48 hours, minute rollups/events after 14 days, and the collector operates under a 512 MiB database-plus-WAL-plus-SHM limit with pressure headroom and documented pinned-reader exceptions. No drive-specific endurance cost, failure rate or installed performance harm has been established from the 0.226 GiB/day difference. The target is now a monitored overhead indicator, not a release blocker. Retain five-second `FULL` commits and SQLite while prioritizing functionality and observed reliability. A partial append-only experiment was stopped after 57 CRC-valid records by this decision; `append-probe-partial.json` is **not** a comparative write result. No new storage engine was installed.

The data-loss window is distinct from the sampling and post-crash outage gaps. At five-second sampling with per-sample `FULL` WAL commits, a successfully committed observation is intended to survive collector and OS crashes or power loss, assuming the filesystem and device honor synchronization; an unfinished observation may be missing. With five-second `NORMAL` WAL commits, a collector-process crash ordinarily leaves committed data readable, but an OS crash or power loss can undo recent commits with **no fixed time bound** from the five-second cadence. A hypothetical six-sample/30-second `FULL` batch would lose up to about 30 seconds of buffered observations on a collector or host crash and delay independent reader visibility by the same amount; under a uniformly timed crash, the mean buffer age would be 15 seconds. That batch was not implemented or profiled. Clean shutdown and the period after a host failure are separate cases. [SQLite's synchronization contract](https://www.sqlite.org/pragma.html#pragma_synchronous) supports the `FULL`/`NORMAL` distinction; the isolated burst `NORMAL` replay cannot predict installed write savings.

Two actual Rust Store optimizations were rejected on measured evidence. `rollup-ab-rust.json` replayed 40 minutes of timestamps in a roughly 1.6-second burst and found that finalizing each minute rollup only once **increased** median physical writes by 6.7%; its timing limits inference about live cadence. `checkpoint-paced-ab.json` used identical real-row fixtures, 512-byte pages, `FULL`/COW, 50 seeded rows and 70 subsequent ticks at five-second spacing. Raising `wal_autocheckpoint` from 1000 to 2000 pages wrote 6,103,040 versus 5,001,216 bytes (+22.0%) in that pair, with integrity checks passing; no setting changed. A separate 36-tick paced attribution (`checkpoint-paced-classes.json`) assigned 69.5% of writes to baseline Store calls, 20.8% to detail calls (including an automatic checkpoint), 8.3% to the explicit final checkpoint, 1.4% to rollup flush and 0% to pruning. The final checkpoint is experiment-end cost, not a steady live operation. These short seeded runs show no demonstrated removable class large enough to close the live 7.6% gap; they do not rule out a different storage-model change.

`gzip-paced-ab.json` compared level-1 and level-6 gzip in the actual Rust Store, each over 120 five-second baseline ticks with seven paired detail ticks, `FULL`/512-byte/COW storage and a final checkpoint. Physical writes fell from 10,158,080 to 8,376,320 bytes (17.54%); serialized sample payload fell 12.10%, Store CPU rose 7.12 ms over 595 seconds, RSS was similar, and all-commit p95 changed from 21.61 to 23.36 ms. Both stores passed integrity checks. This one sequential replay reused captured payloads and omitted live provider sampling and retention, so it could not predict the installed write rate. Astra reviewed level 6 as a reversible candidate. The codec change has a regression check decoding legacy level-1 and new level-6 rows together; the subsequent installed mixed-workload profile is reported above.

Storage now reserves 64 MiB before baseline/detail commits, caps serialized samples at 1 MiB, prunes in 16-row batches with a one-second work budget, and stops repeated deletion while a WAL checkpoint is pinned. An isolated 1,000-row catch-up test committed the next baseline in 124 ms. These are practical pressure guards; an indefinitely held reader or filesystem stall can defeat a strict physical 512 MiB ceiling or five-second cadence. That stronger claim remains unverified.

An isolated five-pair `btrfs-nocow-replay.json` kept SQLite `FULL` and measured 15.6–30.5% fewer physical writes with fresh NOCOW files, median 20.8%; all ten clean-close integrity checks passed. The replay had 2.08% detail duty versus 5.56% in the failed managed mix, so it does not prove the live write target. [Btrfs documents](https://btrfs.readthedocs.io/en/latest/Scrub.html) that NOCOW disables file-data checksums and scrub repair; [in-place updates can suffer partial writes](https://btrfs.readthedocs.io/en/stable/Administration.html) on interruption. NOCOW was not applied to the live database because that integrity tradeoff and fresh-file migration need a separate decision. A clean-close SQLite integrity check does not test host power loss.

The separate `btrfs-page-size-replay.json` tested 1, 2, 4 and 8 KiB pages under `FULL`/COW at 5.625% detail duty; 1 KiB wrote least in all four balanced rounds. `btrfs-page-size-512-replay.json` then compared 512-byte pages against 1 KiB in four more balanced pairs: physical writes fell 10.3–14.7% in every pair, median 14.0%, with all eight clean-close integrity checks passing. This replay was not itself a live write-gate pass. New stores use 512-byte pages. The old 1-KiB installed database was converted through the explicit `st service rebuild summitflow --migrate-monitor-store` maintenance phase. Its protected receipt is `/home/kasadis/.local/state/summitflow/monitor/migrations/page512-1790461929-43a0bb3c/receipt.json`: a retained owner-only backup and matching content fingerprints cover 1,816 samples, 150 rollups, 48 events and four metadata rows. The installed store reports 512-byte pages, WAL, `synchronous=FULL`, `integrity_check=ok`, and resumed collection after the managed restart; the migration interlock was removed after verification. The reader takes a shared lifetime maintenance lock and refuses a surviving interlock, while the migration takes exclusive reader/collector locks, requires matching accepted release markers and free headroom, and leaves an owner-only recovery receipt on failure. [SQLite requires leaving WAL mode to change page size](https://www.sqlite.org/wal.html), and [`VACUUM` needs additional free space](https://www.sqlite.org/lang_vacuum.html).

An agent investigating a slow backend can request status, a 20-point service CPU timeline, then five highest-CPU processes and a few warning events. A disk complaint can request root free space, pressure and disk-write-rate history, then an explicit scoped `disk-space` scan. A suspected service outage can request service state/events and five redacted journal entries. Each step carries time, provider, coverage and errors; the agent follows a returned cursor only if the first page warrants it. Rates compare monotonic time and every contributing device/interface counter; a reset, changed instance, boot, long gap or older row without member evidence yields an unavailable bucket instead of a numeric guess. Linux `ifindex` and block major:minor plus `diskseq` where available identify current members; identifier reuse remains a provider limit.

## Privacy boundary and remaining decisions

The collector, socket and store are owner-file-private and require no elevated service. The HTTP monitor routes require the existing SummitFlow owner principal and reject nonlocal forwarded bypass requests. However, SummitFlow's pre-existing localhost development bypass grants an owner principal to any local HTTP caller. TCP loopback cannot identify Linux UID. Another local account on a multiuser host could read sensitive monitor HTTP data (and other existing local APIs) until the application-wide bypass is replaced with authenticated local sessions. This is an explicit limitation of this Ubuntu single-owner desktop release; do not deploy its HTTP UI on an untrusted multiuser workstation. Cloudflare Access protects the public hostname, and the installed origin-LAN check above was verified. A monitor-only token would narrow direct routes but would not fix other local APIs that can act with the backend owner's authority.

No process kill, service restart, package installation, network benchmark, GPU workload or unbounded filesystem walk is part of observation. Existing guarded `st` operations own state-changing actions. The separate-UID experiment above establishes basic proc/sys visibility and denial behavior; a logged-in plain account is still needed for user-session and journal coverage. Longer mixed-load profiling is useful to track overhead, while quota pressure on the installed btrfs filesystem, alternate Linux desktops and Snap/Flatpak coverage are the smallest further functional experiments. Cross-platform work needs separate macOS/Windows service, log, process identity, sensor, startup, packaging, socket-permission and installer providers plus repeat profiling; the shared schema, pagination and UI can remain. Estimate each new OS after a provider spike, not by assigning a calendar duration now.

## Next execution slices and effort

The installed release is an MVP candidate for a trusted, single-owner Ubuntu desktop. Before calling it an MVP, verify one controlled real logout/reboot with continued collection and stopped-backend reads, then record three bounded agent/UI diagnosis transcripts covering a resource spike, a service/log failure, and a disk or network change. These checks are estimated at 4–8 focused engineering hours. The existing localhost owner bypass precludes a secure multiuser claim. The physical-write target, workload benchmarks, full TMOG parity, and ports to other operating systems are outside this MVP threshold; their current limitations remain visible below.

The first vertical slice is installed: Rust baseline/detail collection, independent history, bounded `st` queries, shared owner Runtime views, retained GPU observations, complete captured process ancestry and isolated restart/WAL checks. Further confidence checks are sustained storage pressure on the installed filesystem, a controlled logout/reboot lifecycle, and a logged-in plain-user session.
