## 0. The argument in five sentences
1. We already run Pi as a first-class harness: tether adapter (aico/tether/src/lifecycle/tui/adapters/pi.ts, 408 LOC), model-switch watch on Pi `responseModel` (tether/src/model-switch.ts header), five live extensions (~/.pi/agent/extensions, 921 LOC: model-guard, publication-guard, agent-hub context delivery, st-coord, aico-due), and a Pi RPC executor in workflow runs (agent-hub executor_pi.py, 318 LOC). B mostly ratifies what runs.
2. Our own harness is a Python port of Pi's shapes (claude_code_cli.py docstring: "a pi-mono ApiProvider like every other provider"; llm/compaction.py:3 "Shaped like Pi's compaction"). We maintain a lagging copy of the thing we would otherwise use.
3. Our gateway has no traffic worth the code: `/api/complete` went from 254 requests on 10-29 to 4 on 10-30 (plan.md A9, line 400) and the cutlist already drops it (ah-02: 33,446 LOC). The real choice is not "keep 28k LOC of Python vs Pi", it is "Pi vs nothing, plus a ~0.5k ask-a-model route" (plan.md:247).
4. Every one of the 7 control lines has a supported Pi mechanism (table below); two need small extensions (Claude CLI provider, refusal categories) that sit on public APIs.
5. Pi's core is small and MIT, so the exit if upstream turns bad is "pin unmodified, or drop to pi-ai/pi-agent-core (21.8k LOC dist) under our own thin loop", never a fork.

### Line 2: model routing at turn level
- Mid-session switch keeping context: `pi.setModel(model)` (we already call it in model-guard.ts "restored = await pi.setModel(previous)"), RPC `set_model`/`cycle_model` (rpc-commands.md:210-250), SDK `session.setModel()` (agent-session.d.ts:663). Cross-provider replay is done by pi-ai `transform-messages` (dist/api/transform-messages.js); custom-provider.md lists "cross-provider session handoff" as a required test [V]. plan.md:454 already assumes this ("In Pi this can stay in the same conversation").
- Fallback chains, automatic: virtual models. `pi.registerVirtualModel({route(request, ctx)})` runs before every request; `request.reason` is user|continuation|retry|direct; `request.failed` carries the failed assistant message (`stopReason`, `errorMessage`); route may return a different physical model, keep `state` on the session branch, and stay sticky to preserve prompt cache. Shipped example jev-router.ts is 113 LOC and switches model mid-task once [V: docs/virtual-models.md, examples/extensions/jev-router.ts]. A role chain (primary, fallbacks, escalation) is a route() reading Aico's `route()` data: ~100-150 LOC [I].
- Substitution detection: `AssistantMessage.responseModel` (pi-ai types.d.ts:374) is already what tether's model-switch.ts reads for Pi. Anthropic path also handles server-side fallback blocks (anthropic-messages.js:505-507) [V].
- Refusal detection: partial. Anthropic `refusal` stop maps to `stopReason:"error"` with `stopDetails.explanation` as errorMessage and the raw stop in `rawStopReason` (anthropic-messages.js:1337-1344, 646); Gemini likewise (`Provider stopped with: <finishReason>`). I found nothing in Pi's Codex provider mapping cyber/bio refusal codes or `model/rerouted` (grep for reroute|cyber|safety in openai-codex-responses.js: no hits) [V negative; U whether the Codex error text carries the code]. Workaround: a ~80-LOC extension using `provider_stream_event` / `after_provider_response` / `message_end` (which can replace the finalized message) to stamp a typed `refusal: {category}` onto the assistant message and `route()` consults `request.failed`. We would port 30 LOC of refusal_codes.py. Cost: small, but it is ours and the Codex payload shape is [U] until tested.
- Per-role model denies: model-guard.ts (165 LOC, running) already enforces launch-defaults deny rows via `session_start`, `model_select`, `before_provider_request` abort. Stronger options under B: (1) per-role credentials: `ModelRuntime.create({authPath, modelsPath})` (examples/sdk/12-full-control.ts:17-20) and `PI_CODING_AGENT_DIR` so a hunting role's Pi has no Anthropic login at all; (2) wrap a provider's `getModels()` to hide denied models (the pattern agent-hub.ts:24-39 already uses for `daybreakProvider`) [V]. Concede: the extension guard is a policy check inside the agent's own process, a hostile prompt cannot remove it, but a hole in Pi's own routes could bypass it; per-role auth files are the real gate.

### Line 3: providers
- Built in (pi-ai/dist/providers): openai-codex (subscription OAuth), opencode, opencode-go, minimax(+cn), google, google-vertex, openai, openrouter, xai, mistral, deepseek, groq, zai, together, etc., plus `models.json` for any OpenAI/Anthropic-compatible endpoint; ollama is documented (docs/models.md:43-65) [V]. This is the line where B beats A the most: new models and API changes (e.g. GPT-6.1 Terra with tool search in 1.5.0, MiniMax-M3.1-Flash in 1.4.0) arrive with `npm update`; in A our team owns 5 provider ports (4.8k LOC) and tracks vendor changes alone.
- Claude only via unmodified `claude` binary: Pi ships an Anthropic provider and an Anthropic OAuth login (CHANGELOG 1.0.0 "Anthropic copy code login"). That is the policy hazard: B must switch it off, not trust people. Mechanisms: remove the Anthropic credential from auth.json/auth path; register an `anthropic` provider override whose `getModels()` returns [] (same pattern as above); keep model-guard's `CLAUDE_PROVIDER = "anthropic"` deny. Then add a custom provider `claude-cli` with `streamSimple` that spawns `claude -p --input-format stream-json --output-format stream-json` tools-off, like our claude_code_cli.py. Doc contract for custom streams: custom-provider.md "Implement custom streaming" (start/delta/done-or-error events, usage, abort, honor `onPayload`/`onResponse`) [V]. Cost: port ~430 (provider) + ~350 (provider_support/claude_stream.py 150, claude_sessions.py 199) Python LOC to ~600-800 TS LOC [I]. It is only needed where Claude must answer inside a Pi conversation; plan.md:247 already routes one-shot Claude calls through a headless CLI, and "Claude coding runs in Claude Code itself" per the brief. So the provider is optional, not on the critical path [I].
- Honest concession: until the override ships, Pi's Anthropic provider exists in the binary. Both our model-guard and a role auth file cover it; neither is "absent from the code".

### Line 6: headless, embeddable, subagents, durable sessions

Embedding choice for Aico's Node 22 server: RPC subprocess per session (isolation, crash containment, fits Tether supervision; Pi requires node >=22.19, matches Aico's Node 22 [V package.json engines]) rather than in-process SDK (extensions are in-process and see credentials per docs/extensions.md intro). Phone/web chat = Aico server holds `RpcClient`, relays events over WS; today's unfinished AgentHubChat.tsx (103 LOC) + chat.ts (200) + agent-hub.ts (58) go away.

## 3. Upstream risk, honestly
Facts [V]: MIT. Repo earendil-works/pi, 119.8k stars, 316 open issues, created 2025-08-09, pushed daily (GitHub API 2026-11-03). Contributors: badlogic 4,167 commits, mitsuhiko (Armin Ronacher) 942, then davidbrai 373, christianklotz 230, cristinaponcela 201, vegarsti 165. Release cadence: 1.0.0 on 2026-10-01; 1.0.1-1.0.4, 1.1.0 (10-07), 1.2.0 (10-12), 1.3.0 (10-15), 1.4.0 (10-21), 1.5.0 (11-02): about one minor per week. Pre-1.0: 290 changelog sections, 50 with "Breaking Changes" (17%); post-1.0: breaking sections in 1.0.3, 1.2.0, 1.5.0 (3 of 11).
What the breaks looked like: provider rename `azure-openai-responses`->`azure` (1.0.3), `before_agent_start` event became a union (1.2.0), custom providers must read system prompt/tools from `TranscriptContext` messages (0.99), `shouldStopAfterTurn` removed (0.99), `SessionManager` made canonical so assigning `agent.state.messages` stopped working (0.99), JSON/RPC `message_update` dropped cumulative `message` (0.86), tool-argument validation moved to `@earendil-works/pi-schema` and TypeBox-only features stop applying (1.5.0). All are compile-time or startup-visible for TS extensions, and each names the migration. The one I would call silent is the 1.4.0 note that `before_provider_headers` handlers no longer see some attribution headers.
Bus factor [I]: effectively two named maintainers plus a company org (Earendil) and ~6 steady contributors; Mario Zechner is the clear single point. Bus factor is lower than Anthropic/OpenAI CLIs, higher than a solo-owner repo like ours (agent-hub: 3,716 commits since 2026-01-04, one owner).
How we pin and upgrade [V/I]: exact version in package.json (cutlist's boundaries.mjs already requires exact-pinned deps); the managed install keeps releases/ side by side with a `current-version` pointer (we have 1.3.0 and 1.4.0 present), so rollback is a pointer flip. Process: bump in a branch, run an Aico contract suite (RPC command/response fixtures, session JSONL fixtures, extension type-check against the new `.d.ts`, one 16-check task per provider), then promote. Upgrade cadence is ours: stay a release or two behind, read CHANGELOG Breaking sections, never auto-update (`PI_SKIP_VERSION_CHECK=1`, `selfUpdateCommand` setting exists as of 1.5.0).
If upstream goes a direction we dislike (no forks, no patched copies): (1) stay pinned on the last good unmodified release (MIT allows it; Pi runs offline with `PI_OFFLINE=1`), (2) every behavior we need is reachable through config/extensions/SDK, which is the supported route, (3) if the extension API itself is removed, drop one layer to `@earendil-works/pi-agent-core` (1.4k LOC) + `pi-ai` (providers, 20k LOC), unmodified, under our own loop, which is the hybrid below, (4) worst case we keep the pinned binary and our extensions and port nothing. What we lose by pinning: new models/providers after the pin (we can still add endpoints through `models.json` and custom providers). The honest weakness is (3): extensions are written against `pi-coding-agent` types which are churnier than pi-ai.

## 4. Hybrid: our thin loop on pi-ai + pi-agent-core
What it is: `Agent` from pi-agent-core (transformContext, convertToLlm, tool execution, events; README lines 40-60) + `createModels()`/providers from pi-ai, our own session store (SQLite) and no TUI. Pi README shows 10 lines to a working agent [V].
Where it beats plain Pi: no 61k-LOC coding-agent package, no TUI, no project-trust/resource discovery, no JSONL file to ingest (store native rows in `node:sqlite`), total prompt/tool control by construction, provider catalog still maintained by Pi team, and an exit ramp with zero fork. Where it loses: we re-own what coding-agent gives for free and has tested: compaction (docs/compaction.md is 463 lines of edge cases: split turns, overflow recovery, file tracking), session tree/branching, retry/overflow recovery, bash/edit/read/write tools with truncation and file-mutation queue, RPC protocol, steering/follow-up queues, TUI for Tether sessions (the owner works in TUIs: Tether runs Pi in tmux). Roughly 4-6k LOC of ours [I].
Verdict: for "the main thing we use" (interactive TUI sessions under Tether, plus headless), plain Pi + extensions wins now, because the owner wants the same agent in the terminal and in the phone UI and Pi's four modes share one agent [V: cli-integration.md]. The hybrid wins only for a special case: Aico-native chat sessions (the "Agent Hub" session type) where a SQLite-native loop with no JSONL is attractive. Recommend: plain Pi now; keep the hybrid as the documented exit and as the way to build any Aico-native chat later (extensions' pi-ai types carry over).

## 5. Measured evidence (brief) [M]
Same 16-check task, gpt-6.1-sol, 16/16 both: ours 30-32k tokens, $0.023-0.032, 29-35 s; Pi 26-35k, $0.019-0.020, 33-44 s; same call sequence. First call: ours 3,778 incl. 2,451 injected shared context that the Pi arm did not get. Per-call overhead without context: ours ~1,000, Pi default ~2,180, Pi + our prompt ~1,730. Read: parity on quality, Pi cheaper in dollars, slower by ~4-9 s (node/RPC startup and compaction checks are plausible causes [I], not investigated). Pi's 700-1,100 extra tokens/call is addressable by tool override but unproven [U]. Pi arm lacked our context, so the dollar comparison is not apples to apples; adding ~2.4k tokens to Pi's first call (cached afterwards) would erase most of its cost edge [I].

## 6. Strongest arguments against B, and my answers
1. "Control: Pi's loop is someone else's; our own harness can do anything." Answer: the seven lines are reachable through documented hooks, and our own harness has never exercised the one thing only an owned loop gives (turn-level switch with context): it has none (packet.py:3). Where Pi would block us (loop semantics), the hybrid is the pre-agreed exit, and pi-agent-core is 1.4k LOC. Risk accepted: extension API churn (about 1 breaking release in 4) costs us maybe a half-day per upgrade, which we gate by pinning. Verified: breaking history above. Unverified: no hook yet found for "stop a tool batch and replace the assistant message mid-stream"; `message_end` replaces finalized messages only.
2. "Churn and bus factor: weekly minors, one dominant maintainer, and Anthropic/Pi could diverge on OAuth policy." Answer: MIT, 120k stars, company-backed org, two top-contributor names; we pin and upgrade on our schedule, and we hold a working copy of the previous release in `releases/`. Our own harness bus factor is 1 (us) plus a port that already trails Pi. Concede: the extension surface moves faster than I like (1.0.3, 1.2.0, 1.5.0 broke extension-facing contracts), and "no forks" means we eat that cost in our code, not theirs.
3. "Claude must stay out of custom clients, and Pi ships Anthropic OAuth." Answer: true hazard. Counter: model-guard already blocks `anthropic` provider for deny roles; add provider override with empty `getModels()` and role auth files without a Claude login; Claude calls go through a `claude-cli` provider or Claude Code itself. A has the same discipline issue (claude_code_cli.py docstring) but with less surface. I concede B adds an always-present code path we have to keep disabled, and I would require a test that fails if Pi can resolve any `anthropic/*` credential in hunting roles [I].
4. "Refusal and substitution handling is what hunting needs, and Pi barely has it." Answer: partly right. Pi gives `stopReason:"error"` plus text for Anthropic refusals, `rawStopReason`, `responseModel` for substitution, and a retry-aware `route()` with `request.failed`. It does not type Codex cyber/bio refusals (negative grep). We add ~80 LOC and port 30 LOC of refusal_codes.py; our existing tether model-switch.ts (960 LOC) already watches Pi and Codex records and stops the lane. Net: the refusal pipeline we have is mostly outside the harness (tether), so B does not weaken it; what B adds is the option for in-conversation handoff (plan.md:454), which A cannot do.
5. "Pi is a TUI-first product; embedding it in a lean Aico adds a 61k-LOC dependency and a Node subprocess per chat, and Pi was 4-9 s slower in the measurement." Answer: we embed via RPC (supported, typed `RpcClient`), not in-process, so the 61k LOC stays out of our build and our `packages/` LOC cap; per-session subprocess matches Tether containment. The latency delta is on one 16-check task and we have not isolated cause; I would not block on it but would re-measure with the tool overrides applied. Concede dependency size: node_modules for Pi 1.4.0 is large (aws-sdk, smithy, protobufjs, google-auth, etc. in the install tree) [V: ls], a supply-chain surface bigger than our Python-only provider set; mitigate by running as a pinned install and `--offline`.
6. (Extra) "Pi does not ask approval and has no sandbox." Answer: neither does our harness (section 1). Containment is Tether/VM in both; B can add the official bubblewrap example per role.

## 7. Recommendation for option B in one block
Make Pi (pinned, unmodified, offline, telemetry off) the single agent loop for Aico's coding/ops/hunting lanes; drive it from Aico's TS server over `RpcClient`; own one small `aico-pi` extension package (tools override, role context delivery, router/fallback via virtual model, refusal typing, model/publication guards, optional claude-cli provider) with contract tests; keep Claude Code and Codex CLIs as their own harnesses; keep pi-ai/pi-agent-core as the documented exit. Delete ah-02's providers/tool loop (agree with cutlist), keep the 0.5k ask-a-model route, and reuse executor_pi.py's lessons in the TS RPC driver.

Open items I could not verify (label U): exact Codex refusal payload text in Pi; resulting token count after tool overrides; whether SDK sessions can write through to a non-JSONL store; behavior of 1.5.0 vs our extensions; whether `registerProvider("anthropic", {getModels: () => []})` truly hides built-in models (the pattern for `openai` is used in agent-hub.ts:24-39, the `anthropic` case is by analogy).
