Author: advocate for A. Read-only review. Tags: [V] verified in source/docs I read, [I] inference, [U] unverified.
Paths: AH = /srv/workspaces/projects/agent-hub/backend/app. AICO = /srv/workspaces/projects/aico.
PI = ~/.pi/agent/install/releases/1.4.0/node_modules/@earendil-works (local Pi 1.4.0, 2026-10-21). PIDOCS = PI/pi-coding-agent/docs.
Note: the brief says badlogic/pi-mono; the installed packages and docs point to github.com/earendil-works/pi (MIT) [V: PI/pi-ai/package.json, PIDOCS/extensions.md]. Old changelog entries still use badlogic/pi-mono and the scope @mariozechner (PI/pi-coding-agent/CHANGELOG.md:2230, :2582), so Pi has already moved org, repo and npm scope once.

## 0. Verdict up front (honest)

- Best form of A is NOT "rewrite 20k lines of providers". It is: **own thin harness in TypeScript, providers from pi-ai as a pinned library, loop on pi-agent-core, everything policy-shaped owned by us.** The hybrid clearly beats a full own build. [I, backed by section 3]
- Hybrid-A vs B (Pi as the product) is closer than the brief's framing suggests. Pi can do most of the 7 lines through extensions. A's edge is "by construction, in one process, in our store" vs "bolted onto someone else's 64k-line product that changes every few days". I mark where Pi truly cannot and where it just does it awkwardly.
- A has real costs (no TUI, we rebuild resume/branching/compaction, we own ~5k lines). Section 6 answers the strongest objections; I concede where I cannot answer.

## 1. Language choice (on merit)

**TypeScript on Node 22 for the loop, provider glue, tool runtime and session store.** Reasons:
1. pi-ai (~20k JS lines, MIT) and pi-agent-core (~1.4k) are TypeScript/ESM [V: wc of PI/pi-ai/dist, PI/pi-agent-core/dist, excluding model data]. Our Python harness is a hand-port of the same shapes (AH/llm/outcomes.py:1-9 says "locked pi-mono set"; claude_code_cli.py docstring "a pi-mono ApiProvider"). A port lags upstream forever; in TS we import the real thing. This is the decisive reason.
2. Aico is TS/Node + `node:sqlite` per machine (cutlist.md:5). An in-process loop writes transcripts, usage and outcomes straight into the session store; no HTTP gateway, no Postgres, no Hatchet (cutlist ah-01 drops 51k lines of that foundation).
3. Tether (TS) supervises processes via tmux; the harness is just another child under it, bundled by esbuild into one file that runs on VM 200/201 with only Node installed [I; same deploy shape as cutlist.md:1.4].
4. Hunting sandboxes and remote hosts are not a language question: sandbox = external bwrap/netns/VM boundary configured by data; remote = same bundle on the host, Tether placement.

**Parts that should differ:** the shell guard stays the Go `aico-hook` (cutlist.md:19, already data-driven; Python's command_guard.py:1-168 is already just a thin adapter to it). The root host checks stay Python. Rust: no gain (I/O bound, no pi-ai). Python: no.

## 2. The 7 lines, Pi vs our harness

Verdict key: **A+** Pi cannot / awkward by design; **tie** Pi can do it about as well; **B+** Pi is better today.

### Line 1. Exact context control, no hidden harness text: tie, slight A+
Ours [V]: system prompt and tool list are data per level in `AH/services/workflow_runs/executor_defaults.json:54-119` (read = 1 tool, lean = 5 tools, full = null); loop-side pruning in `AH/llm/headroom_compress.py:1-40` (flag-gated, lossless, idempotent, never touches thinking signatures), spill-to-searchable-scratch for big output in `AH/services/tools/scratch_context.py` (371 lines), compaction in `AH/llm/compaction.py:306` (`Compactor`). Brief: ~1,000 tokens harness overhead per call vs Pi lean ~1,730.
Pi [V]: Pi CAN reach exact control: `customPrompt`/`forceSystemPrompt` (PI/pi-coding-agent/dist/core/system-prompt.js:63-90), tool override by name (examples/extensions/tool-override.ts), `context`/`tool_result` hooks (PIDOCS/extensions.md "Choose an event by intent"). The remaining differences:
- Without a custom prompt Pi injects its own preamble, a "Pi documentation" block and always-on rules ("Be concise...", system-prompt.js:63, :83-88). Replaceable, but it is default-on text per release.
- Default-on background behaviour: `cacheWarming` defaults to `"streaming"` (provider requests that "count toward session totals", PIDOCS/settings.md:20-23); `enableInstallTelemetry` true (settings.md:165-171); model-catalog refresh and version check on unless `PI_OFFLINE`/`PI_SKIP_VERSION_CHECK` (PIDOCS/environment-variables.md:84-86). Each is switchable, but each release can add another.
- Tool/prompt changes mid-run are appended to the transcript as system messages, and "providers that cannot represent the transition receive a complete transcript checkpoint, which can invalidate the cached prefix" (PIDOCS/extensions.md, "Activate tools dynamically"). Our prefix is whatever we send.
- 1.4.0 narrowed an extension's view: attribution headers "no longer" visible to `before_provider_headers` (CHANGELOG.md:23). Control erodes by changelog.
Honest: with ~100 lines of settings plus an override extension Pi gets within ~700 tokens of ours (brief). A wins on guarantee, not on capability.

### Line 2. Turn-level routing, refusal/substitution, handoff, per-role denies: A+ on outcomes and denies, B+ on turn-level switching today
Ours [V]:
- Typed provider outcomes on the assistant message: `refused | substituted | usage_limit | interrupted` (`AH/llm/utils/outcomes.py:1-34`), set at wire level. Codex: refusal codes (cyberPolicy, bioPolicy, tooManyDenials) mapped in `AH/llm/utils/refusal_codes.py:8-17`, raised at `openai_codex_responses.py:535-546`, recorded at `:706-723`; served-model substitution from `response.model` at `:668-684`. Claude CLI: `claude_stream.py:122-150` maps fallback/refusal/rate-limit records to outcomes; `claude_code_cli.py:1-30` documents that fallback is disabled so a flagged request is never silently re-run elsewhere.
- Policy is pure functions over those outcomes: `AH/services/workflow_runs/policy.py:175-203` (`choose_attempt_model`), `:243-275` (`_move_on`, hop record, pause reasons). This ports to TS nearly line for line [I].
Pi [V]:
- Pi's Codex path throws `CodexApiError` with the raw `code` (PI/pi-ai/dist/api/openai-codex-responses.js:561-566) but has no refusal categories, and the Responses parser records `responseId` only (openai-responses-shared.js:503, :546); `responseModel` is set only in anthropic-messages (:485-487) and openai-completions (:361). So a Codex substitution inside Pi is invisible at the provider layer. This is why Tether tails transcripts after the fact: `AICO/tether/src/model-switch.ts:1-40` (960 lines) reads each tool's own record and presses Escape when a fallback model answers. Fixable in a hybrid via pi-ai's `onProviderStreamEvent` (pi-ai/dist/types.d.ts:118), without a fork [V that the hook exists; I that it suffices].
- Per-role denies in Pi today = `~/.pi/agent/extensions/model-guard.ts` (165 lines): fetches rules over HTTP from Agent Hub (`:14`), 2 s request timeout (`:17`), and when the lookup fails it **allows** and pauses lookups for 60 s (`:19, :85-98`, comment "Unreadable rules keep the session's choice"). A denied provider request can only be stopped with `ctx.abort()` because "a throw here is only reported" (`:143, :158`). That is a fail-open, network-dependent deny for roles (hunters) where it must be fail-closed. Fixable in Pi, but the structure (hook inside a process whose loop doesn't know about role) is why it looks like this.
- Turn-level switching: Pi is AHEAD. `registerVirtualModel` routes every request, sees `failed` on retry, keeps router state in the session (PIDOCS/virtual-models.md), and `pi.setModel()` keeps the conversation (plan.md:453). Our Python harness does NOT route per turn: fallback is whole-request (`AH/api/complete/execution.py:111-153`) or per attempt with a new session and handoff packet (policy.py). Turn-level routing in A is therefore new work, easy on pi-agent-core: `prepareRequest` can swap `model`/`thinkingLevel`/`context` before each request (pi-agent-core/dist/types.d.ts, `PrepareRequest`; README "Request preparation").

### Line 3. Providers: B+ over a full own build, tie for the hybrid
- pi-ai ships every provider we need: openai-codex (+ChatGPT OAuth), opencode-go, minimax(+cn), google/vertex, openai, openrouter, faux, plus custom-provider registration for ollama/llama.cpp (PI/pi-ai/dist/providers/*.js; README "Custom Providers" ~:1266-1300) [V]. Our Python equivalents (anthropic.py 1043, openai_completions.py 1322, google.py 685, codex 755) are a lagging subset. Rewriting these in Rust/Go/TS would be wasteful. Take pi-ai.
- Provider drift is real and Pi absorbs it: 1.3.0/1.4.0 alone fixed OpenCode Go endpoint moves, MiniMax protocol choice, Gemini thinking budget, whitespace-only tool output causing 400s, Codex model list errors (CHANGELOG.md, 1.3.0 and 1.4.0 "Fixed"). A hybrid inherits those for free. Hard rule from CLAUDE.md: never fork third-party code, so we consume pi-ai as an exact-pinned dependency (Pi itself pins its internal deps exactly, CHANGELOG.md:81).
- Claude: Pi/pi-ai SHIPS Claude subscription OAuth with Claude Code identity: stealth tool naming "Mimic Claude Code's tool naming exactly" (pi-ai/dist/api/anthropic-messages.js:42-44), a forced "You are Claude Code, Anthropic's official CLI for Claude." system block for OAuth tokens (:927-932), OAuth client flow (auth/oauth/anthropic.js). `/login` offers it (PIDOCS/providers.md:12), and the model-guard exists because "Pi shares one login file" (model-guard.ts:4). That is exactly the path the brief says Anthropic forbids. In a hybrid we simply never register the anthropic provider, and our `claude-code-cli` provider (AH/llm/providers/claude_code_cli.py:1-30, unmodified `claude -p`, tools denied, never touches Claude credentials) is the only Claude route. In B the forbidden path is one `/login` away in the product the owner uses daily [V that it exists; the policy conclusion is the brief's].
- Things only we have today (carry over): claude-code-cli provider (427 + ~410 support lines), Codex outcome mapping (~150), API key pool with billing-failure cooldown (api_key_pool.py, 141) [pi-ai equivalent U].

### Line 4. Tool policy, publication guard, sandbox/egress, containment, remote hosts: tie on mechanism, A+ on where the policy lives
- Levels read/lean/full are identical in effect: ours `executor_defaults.json:8, 36-52`; Pi `--tools read,grep,find,ls` (we already use it, executor_defaults.json:29-42). Pi extensions can wrap bash (`bash-spawn-hook.ts`), route to SSH (`ssh.ts`), run in a micro-VM (`gondolin`) [V: PI/pi-coding-agent/examples/extensions].
- Pi states plainly that it has no sandbox and that extensions run in-process with full permissions: "Pi can read, change, and execute files with the permissions of the account that started it" (PIDOCS/security.md:1-3); lack of built-in sandbox is "outside the security boundary" (security.md, last paragraph); Gondolin leaves "other extension tools" on the host and commands "inherit host environment variables" (PIDOCS/containerization.md). So hunting needs the same external boundary under B and A. No Pi advantage and no A advantage on isolation itself.
- A advantage is where the rules sit. Our publication guard is the shared hook invoked from our tool runtime; in Pi it is an extension that re-spawns the hook per bash call (`~/.pi/agent/extensions/publication-guard.ts:1-50`), model deny is a second extension (model-guard), SummitFlow coordination a third (st-coord.ts 179), due/timing a fourth (aico-due.ts 176), context delivery a fifth (agent-hub.ts 319): 921 lines across five files, each exposed to Pi's extension API churn (57 event interfaces in 1,757 lines of `extensions/types.d.ts` [V]). In A the same policy is one `RolePolicy` object read by the loop and the tool runtime: role -> allowed models, tool level, guard on/off, egress profile. Fail-closed by default because the loop owns the call [I].
- Process containment under Tether is the same either way (child under tmux, own process group; ours is `AH/services/workflow_runs/processes.py`, 379 lines, ports directly).

### Line 5. Observability and transcripts into Aico's store: A+
- Ours [V]: per-call `request_metrics` incl. `max_gap_s`, keepalives, total time, retry log (`AH/llm/tool_loop.py:223-270`); "silence and elapsed time never end a request", only a wire-silence bound (`AH/llm/utils/stream_timeout.py:1-6`, matches owner rule M:fb9ffed9). Pi's defaults are equivalent (`httpIdleTimeoutMs` 300000, PIDOCS/settings.md:126), so this is a tie on behaviour.
- Pi usage/cost per message and `/session` totals are good; pi-ai has OTel-style spans with token counters (pi-ai README ~:1132-1141). Tie.
- Transcripts: A+ and verified. Pi persists JSONL files; `SessionManager` is a concrete class with a private constructor and only file or in-memory persistence (pi-coding-agent/dist/core/session-manager.d.ts:222-234, :371-386). There is no pluggable store, and the SDK says assigning messages does not replace persisted context (PIDOCS/sdk.md "Session storage"). To get Pi sessions into Aico we must find and tail files: `AICO/tether/src/lifecycle/tui/adapters/pi.ts:1-50, :128-175` scans `~/.pi/agent/sessions/--<cwd>--/<time>_<id>.jsonl`, and Pi-specific reading is also in model-switch.ts. The plan's own transcript-ingestion row is 19.5k lines to be rebuilt as "one reader per tool" (cutlist.md ah-08). With our own loop the harness writes SQLite rows as it goes: no reader for the main agent.

### Line 6. Headless/embeddable, phone, subagents, durable sessions: B+ on features, A+ on fit
- Pi SDK and RPC are good and documented (PIDOCS/sdk.md, rpc.md, rpc-commands.md 860 lines). Concede: for an embeddable agent Pi is a real library. Limits [V]: RPC extension UI forwards dialogs but "not custom terminal components" (extensions.md "UI and modes"); one Pi process per RPC session; session store as above; `SessionManager` canonical-context change broke SDK hosts in 0.87 (CHANGELOG.md:543).
- Pi's tree sessions, branching, resume, `/tree`, compaction are mature (PIDOCS/sessions.md, compaction.md 463 lines). Our harness has none of that on SQLite yet: its session ledger lives in Postgres and is dropped (cutlist ah-05). A must rebuild resumable sessions; this is the biggest build item. Honest B+.
- Aico UI: `AICO/web/frontend/components/AgentHubChat.tsx` (103 lines) and `web/server/src/chat.ts` (200) are unfinished and forward through Tether to the Python gateway (`tether/src/agent-hub/runtime.ts`, 762). With an in-process TS harness they bind to the same store the rest of Aico uses. With Pi they bind to an RPC child plus a JSONL tailer. Phone access is the same web path either way [I].
- Subagents/workflows: Pi core has none (a `subagent` example only; "in-process subagents" appear in codemode, CHANGELOG.md 1.4.0). Ours is workflow_runs, 8.3k lines, which the plan drops (cutlist ah-09). A would add only a minimal "run a role headless with a packet" (~500 lines) [I].

### Line 7. Maintenance, LOC, upgrade risk, lock-in: honest split
- Pi's own cost to us [V]: since 2026-07-01 there were 35 releases, 9 with a "Breaking Changes" section (awk over PI/pi-coding-agent/CHANGELOG.md). Examples hitting exactly our surface: pi-ai stream input changed from `Context` to `TranscriptContext` (:603); `SessionManager` made canonical, `turn_end` event reshaped, `shouldStopAfterTurn` removed (:541-545); `user_bash` fails closed (:605); attribution headers hidden from extensions (:23); org/repo/scope rename (:2230, :2582). Our exposed surface in B: 921 extension lines + the 408-line Tether adapter (adapters/pi.ts) + Pi parts of model-switch.ts, plus the CLI flags Tether passes (`--session-id`, `--approve`, `--no-extensions`).
- The hybrid is not free of this: pi-ai and pi-agent-core also break (the `TranscriptContext` change is a pi-ai change). Mitigation: exact pin, one adapter file between our code and pi-ai types, faux-provider + recorded-stream replay tests (pi-ai ships a `faux` provider, README ~:1493-1569), bump on our schedule, never auto-upgrade a running host.
- Lock-in: B couples daily work to one org's product direction (codemode, MCP, Radius, TypeSafe classifiers in 1.x). A-hybrid couples only to MIT libraries we can pin forever; worst case we freeze pi-ai at a known-good version and patch around it in our code (not in theirs).
- LOC we would own (A-hybrid) [I, estimates]: loop + policy glue 0.8-1.2k; claude-cli provider 0.6k; Codex outcome decorator 0.2k; tools (bash/read/edit/write/scratch/levels) 1.2-1.8k; SQLite session/transcript/usage/resume 0.8-1.2k; subagent/handoff 0.5k; tests extra. Total about 4-6k TS lines, vs 28k Python today (10.1k llm + 9.3k complete + 8.3k workflow_runs) and cutlist's planned 0.5k "ask a model" route. B owns about 1.3-1.5k (extensions + adapter) but zero control of the 64k-line host [V: pi-coding-agent dist is ~64k JS lines].

## 3. Target design

Scope (one package, `packages/agent`, layer 3 in cutlist.md:1.1, imports store/shared/context only; no HTTP gateway):
1. `models`: pi-ai `createModels()` with only the providers we allow registered (codex, opencode-go, minimax, google, openai, custom ollama, our `claude-code-cli`). The Aico `models` data file + `route()` (cutlist ah-20) decides; pi-ai supplies catalog and wire format.
2. `loop`: pi-agent-core `Agent`, with hooks we fill: `prepareRequest` (role deny check against in-memory policy, model swap on handoff, scratch/pruning), `beforeToolCall`/`afterToolCall` (guard hook, level check, scratch spill, usage), `finishTurn` (end/continue on typed outcomes). Our own decorator around `streamFn` reads `onProviderStreamEvent` to attach `ProviderOutcome` (port of outcomes.py and refusal_codes.py).
3. `tools`: own bash/read_file/edit_file/write_file/search_scratch_context + level provisioner (data), calling the Go `aico-hook`.
4. `session`: SQLite rows (messages, usage, outcomes, handoffs), resumable by id; export to a JSONL for archive if wanted.
5. `cli/serve`: `aico agent run --role X` headless, plus the route the Aico UI chat uses; Tether launches it like any other tool. Interactive terminal work stays in Claude Code/Codex/Pi TUIs through Tether adapters (unchanged).

Carries over from Python: outcomes.py, refusal_codes.py, policy.py (pure), packet/handoff shapes (packet.py 416), transform rules (transform_messages.py 237; pi-ai has its own `transform-messages.js`, prefer it), compaction policy (404) re-expressed, scratch_context (371), executor_defaults.json level data (as-is), claude CLI provider (~840 lines), api_key_pool (141). Does not carry: FastAPI/Postgres/Hatchet, SSE gateway, executors for pi/codex/claude_code (Tether runs those TUIs), engine.py (2.5k).

Keeping up with providers/auth/models: (a) pi-ai bump on a schedule with replay-fixture tests; (b) catalog is data, new models are a row; (c) Codex OAuth via pi-ai's `auth/oauth/openai-codex.js` into our own `CredentialStore` (pi-ai README ~:461 `createModels({credentials})`), keeping secrets in the Aico secrets folder; (d) Claude never leaves the `claude` binary; (e) a nightly smoke that calls each registered provider once with a tiny prompt and writes a Status row, so drift is visible before a hunt hits it [I].

Hybrid vs full own build: hybrid wins decisively on providers (20k lines we will not track). On the loop it is close: pi-agent-core is 1.4k lines with the hooks we need [V], but its hooks have changed (`shouldStopAfterTurn` removed). Plan: use it behind our own 100-line `AgentRun` interface; if it breaks twice, write our own loop (our Python loop is 479 lines, tool_loop.py) rather than fork theirs.

## 4. Why this is not just "Pi with extra steps"

Under B every guarantee is a handler in Pi's process: deny model (fail-open lookup, abort-only), publication (spawn per call), substitution (transcript tail + Escape), transcripts (file tail), context delivery (extension). Under A the loop IS the guarantee: it sees the typed outcome, knows the role, writes the row. The cost is the product surface (TUI, branching, skills, MCP) which, for headless Aico work, we mostly do not need [I].

## 5. Measured parity, stated plainly

Same 16-check task: ours 30-32k tokens / $0.023-0.032; Pi 26-35k / $0.019-0.020 (brief). Pi is not worse and is slightly cheaper. The measured 2,451-token gap in first call is Agent Hub context injection, not the harness. I do not claim a performance or cost win for A.

## 6. Strongest arguments against A, and my answers

1. **Usage is near zero: gateway traffic fell to 4 requests on 10-30 (plan.md A9, "254 on 10-29, 4 on 10-30"); the owner already works in Pi/Codex/Claude TUIs; the plan drops the gateway (cutlist ah-02).** Answer: the traffic was a deprecated Python HTTP path, and its UI (AgentHubChat) is unfinished [V]; why use fell is [U]. But this is a real risk: A only pays if Aico chat and hunting actually run through it. Gate: build the vertical slice (one role, Codex, bash/edit, SQLite transcript, role deny, outcome handoff) and judge it before investing in resume/branching.
2. **Pi is a living product with TUI, skills, MCP, packages, 120k stars; we can never match that and a thin harness will rot.** Answer: concede for interactive use; keep Pi as one Tether adapter beside Claude Code and Codex for that. A targets the headless, policy-heavy work; skills are files and need no runtime, and MCP is unneeded for our roles. Rot is bounded by the 4-6k size and by pinning pi-ai.
3. **More code we own (4-6k vs ~1.4k) and rebuilt resume/compaction/branching that Pi already has.** Answer: partly unanswerable. Owned LOC is higher; resume and compaction are real work (compaction.py already exists as reference). What B owns is smaller but sits on a surface that broke in 9 of 35 recent releases and still needs a file-tailing reader (pi.ts + 19.5k-line ingestion class of work). I claim lower exposure, not lower LOC.
4. **Pi already has turn-level routing, virtual models, refusal fallback for Anthropic, `setModel` handoff in the same conversation; ours does not (execution.py:111, policy.py are request/attempt level).** Answer: agreed, and the plan's optional hand-off item (plan.md:453) works in Pi. What Pi lacks is typed Codex refusal/substitution outcomes and fail-closed role denies. Both are small extensions, so B can close the gap (about 300 lines on `after_provider_response`/`provider_stream_event` [I]). Real remaining difference: whether those live in an extension or in the loop. This is the weakest part of my case; the call is a judgment on control vs ecosystem.
5. **Provider/auth churn will be on us (Codex OAuth, OpenCode endpoints, MiniMax protocols).** Answer: not under the hybrid: pi-ai carries it and we take bumps. A full own build would fail this test, so I do not propose one.
